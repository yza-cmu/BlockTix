GAS OPTIMIZATION OPPORTUNITIES
===============================

[OPT-1] Make Contract References Immutable
-------------------------------------------
Priority: HIGH
Impact: Medium (saves ~2100 gas per SLOAD operation)
Difficulty: Easy

Current Issue:
In BlockTixMain.sol, the ticketNFT and priceOracle contract references are set
in the constructor but not declared as immutable. Slither flagged this.

Location:
- BlockTixMain.sol line 16: ITicketNFT public ticketNFT;
- BlockTixMain.sol line 17: IPriceOracle public priceOracle;

Optimization:
Change to immutable declarations:
```
ITicketNFT public immutable ticketNFT;
IPriceOracle public immutable priceOracle;
```

Gas Savings:
- Each SLOAD from storage costs ~2100 gas
- SLOAD from immutable costs ~3 gas (embedded in bytecode)
- Savings: ~2097 gas per reference read
- purchaseTicket() reads both: ~4194 gas saved per purchase
- Estimated total savings: ~4000-5000 gas per ticket purchase

Rationale:
These references are set once in constructor and never change. Making them
immutable saves storage reads and reduces gas costs for every function that
uses these contracts.


[OPT-2] Cache Array Length in Loops
------------------------------------
Priority: MEDIUM
Impact: Low-Medium
Difficulty: Easy

Current Issue:
In PriceOracle.getLatestPrice(), the array length is accessed directly in
the comparison, which requires a storage read.

Location:
- PriceOracle.sol line 285: if (history.length == 0) return 0;
- PriceOracle.sol line 286: return history[history.length - 1].price;

Optimization:
```
uint256 historyLength = history.length;
if (historyLength == 0) return 0;
return history[historyLength - 1].price;
```

Gas Savings:
- Small savings (~100-200 gas) per call
- Not frequently called, so total impact is low

Status: OPTIONAL - low impact


[OPT-3] Optimize Event Struct Packing
--------------------------------------
Priority: MEDIUM
Impact: Medium (saves storage slots)
Difficulty: Medium

Current Issue:
The Event struct in BlockTixMain.sol uses multiple uint256 fields that could
be packed more efficiently.

Location:
BlockTixMain.sol lines 23-33

Current Struct (8 storage slots):
```
struct Event {
    uint256 eventId;           // slot 0
    address organizer;         // slot 1 (20 bytes, wastes 12 bytes)
    string name;               // slot 2+
    uint256 totalTickets;      // slot n
    uint256 ticketsSold;       // slot n+1
    uint256 basePrice;         // slot n+2
    uint256 eventDate;         // slot n+3
    bool isActive;             // slot n+4 (1 byte, wastes 31 bytes)
    uint256 maxResaleMarkup;   // slot n+5
}
```

Optimization Possibility:
Pack address + bool + smaller uints together. However, this requires careful
consideration of the max values needed:
- eventId: could use uint64 (max 18 quintillion events)
- totalTickets: could use uint32 (max 4 billion tickets per event)
- ticketsSold: could use uint32 (must match totalTickets size)
- maxResaleMarkup: could use uint16 (max 65535 basis points = 655%)

Packed Struct (4-5 slots):
```
struct Event {
    uint64 eventId;
    address organizer;         // Pack with eventId in slot 0
    uint32 totalTickets;
    uint32 ticketsSold;        // slot 1
    uint128 basePrice;         // slot 1 (partial)
    uint64 eventDate;          // slot 2
    bool isActive;
    uint16 maxResaleMarkup;    // slot 2
    string name;               // slot 3+
}
```

Gas Savings:
- Saves 3-4 storage slots per event
- Event creation: ~60,000-80,000 gas saved (20k per slot)
- Event reads: ~6,000-8,000 gas saved per read

Risk Assessment:
- uint64 eventId: Safe (would take billions of events to overflow)
- uint32 tickets: Safe for most events (4 billion ticket limit reasonable)
- uint128 basePrice: Safe (max ~340 undecillion wei, plenty for any price)
- uint64 eventDate: Safe until year 2554 (Unix timestamp fits)
- uint16 maxResaleMarkup: Safe (655% max markup is reasonable)

Status: RECOMMENDED but requires testing

Difficulty: Medium

Gas Savings:
- Saves 2 storage slots per ticket
- Ticket creation: ~40,000 gas saved
- Ticket reads/updates: ~4,000 gas saved per operation

Risk Assessment:
- uint128 ticketId: Very safe (max 340 undecillion tickets)
- uint128 eventId: Very safe
- uint128 purchasePrice: Safe (same as Event.basePrice reasoning)

Status: RECOMMENDED


[OPT-5] Remove Redundant ticketToEvent Mapping
-----------------------------------------------
Priority: HIGH
Impact: High
Difficulty: Easy

Current Issue:
BlockTixMain stores a redundant ticketToEvent mapping when the same information
is already stored in the tickets mapping.

Location:
- BlockTixMain.sol line 46: mapping(uint256 => uint256) public ticketToEvent;
- Used in: line 174 (purchaseTicket)

Analysis:
The tickets[ticketId].eventId already contains this information. The separate
ticketToEvent mapping is redundant.

Optimization:
Remove the ticketToEvent mapping entirely and access via tickets[ticketId].eventId
when needed.

Gas Savings:
- Saves 1 SSTORE per ticket purchase: ~20,000 gas
- Saves storage slot permanently

Risk:
Very low - the data is already available in tickets mapping

Status: HIGHLY RECOMMENDED


[OPT-6] Unchecked Math Where Safe
----------------------------------
Priority: MEDIUM
Impact: Low-Medium
Difficulty: Medium

Current Issue:
Some arithmetic operations are safe from overflow/underflow but still incur
the overhead of checked math in Solidity 0.8+.

Locations:
1. TicketNFT.sol line 64: tokenId = _tokenIdCounter++;
   - Safe: counter only increments, won't realistically overflow uint256

2. BlockTixMain.sol line 175: eventData.ticketsSold++
   - Already checked: line 159 ensures ticketsSold < totalTickets

Optimization:
Use unchecked blocks for these operations:
```
unchecked {
    uint256 tokenId = _tokenIdCounter++;
}
```

Gas Savings:
- Saves ~20-40 gas per operation
- Accumulates over many ticket purchases

Status: OPTIONAL - small gains, adds complexity


[OPT-7] Optimize Price History Storage
---------------------------------------
Priority: LOW
Impact: Low (but improves scalability)
Difficulty: Hard

Current Issue:
PriceOracle stores unlimited price history in a dynamic array. For events with
many ticket sales, this array grows unbounded, making getPriceHistory() very
expensive.

Location:
- PriceOracle.sol lines 94-96, 138-140

Analysis:
Price history is useful but unlimited storage is expensive. Most use cases
don't need complete history.

Optimization Options:
1. Limit history to last N entries (e.g., 50)
2. Use a circular buffer
3. Separate cold storage for old history

Gas Impact:
- Current: O(n) cost for array push grows over time
- With limit: Constant cost after reaching limit

Status: FUTURE ENHANCEMENT - not critical for current scale
