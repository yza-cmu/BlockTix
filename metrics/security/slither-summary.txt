[MEDIUM-1] Reentrancy Vulnerability in BlockTixMain.withdraw()
---------------------------------------------------------------
Location: src/BlockTixMain.sol#268-282
Severity: Medium
Category: Reentrancy (state modification after external call)

Description:
The withdraw() function makes an external call to transfer ETH on line 275,
then writes to the pendingWithdrawals mapping on line 277 when the transfer
fails. This violates the checks-effects-interactions pattern and could allow
reentrancy attacks if the nonReentrant modifier is removed or bypassed.

Code Location:
```
function withdraw() external nonReentrant {
    uint256 amount = pendingWithdrawals[msg.sender];
    if (amount == 0) revert NoWithdrawalAvailable();
    pendingWithdrawals[msg.sender] = 0;

    (bool success, ) = msg.sender.call{value: amount}("");
    if (!success) {
        pendingWithdrawals[msg.sender] = amount;  // <-- STATE CHANGE AFTER CALL
        revert WithdrawalFailed();
    }
    emit WithdrawalProcessed(msg.sender, amount);
}
```

Risk Assessment:
While the nonReentrant modifier provides protection, restoring state after an
external call is still a bad practice. If the modifier is ever removed during
refactoring, this becomes a critical vulnerability.

Impact: Medium - Could allow reentrancy if protections are weakened
Likelihood: Low - Currently protected by nonReentrant modifier
Overall: Medium severity issue that should be fixed

Status: TO BE FIXED

[FIX-1] Medium Severity - BlockTixMain.withdraw() Reentrancy
-------------------------------------------------------------
Status: FIXED
Date Fixed: 2025-11-11
File: src/BlockTixMain.sol
Function: withdraw() (lines 268-284)

Issue Summary:
The withdraw() function was restoring state (pendingWithdrawals[msg.sender])
after making an external call to transfer ETH. This violated the CEI pattern and
could enable reentrancy attacks if the nonReentrant modifier was ever removed.

Original Code Pattern:
```
pendingWithdrawals[msg.sender] = 0;
(bool success, ) = msg.sender.call{value: amount}("");
if (!success) {
    pendingWithdrawals[msg.sender] = amount;  // BAD - state change after call
    revert WithdrawalFailed();
}
```

Fix Applied:
Removed the state restoration after the external call. Now if the transfer fails,
the function simply reverts without restoring the balance. The user can retry
the withdrawal since the balance was cleared before the call attempt.

Fixed Code Pattern:
```
// Clear balance before external call (checks-effects-interactions pattern)
pendingWithdrawals[msg.sender] = 0;

(bool success, ) = msg.sender.call{value: amount}("");
if (!success) {
    // Don't restore state after external call - just revert
    // User can try withdrawal again, nonReentrant protects against exploits
    revert WithdrawalFailed();
}
```

Rationale:
- Follows proper CEI pattern by never modifying state after external calls
- The nonReentrant modifier provides defense-in-depth protection
- If transfer fails, user simply calls withdraw() again
- Eliminates any potential reentrancy risk even if modifiers are changed later

Testing Impact:
This change should not break existing tests since the end result is the same -
failed withdrawals still revert. The only diffrence is the pending balance
remains at zero after a failed attempt instead of being restored.


[FIX-2] Low Severity - TicketNFT.mint() Reentrancy

[FIX-3] Low Severity - TicketNFT.batchMint() Reentrancy

File: src/TicketNFT.sol

Similar to mint(), the batchMint() function was updating state after calling

```

```

Fix Applied:

mapping and tokenIds array assignment) happen before the _safeMint() call.

Fixed Code Pattern:
```
for (uint256 i = 0; i < amount; i++) {

    // Set state before external call (checks-effects-interactions pattern)

    tokenIds[i] = tokenId;

    _safeMint(to, tokenId);

    emit TicketMinted(tokenId, to, eventId);
}
```

Rationale:
- Applies the same CEI pattern fix as mint() to maintain consistency
- Each loop iteration now properly sequences operations
- Eliminates reentrancy concerns in batch operations
- No functional change, just reordering for security best practice

Testing Impact:
No impact expected. The state updates can happen before minting without any
functional difference. All batch minting tests should pass unchanged.
